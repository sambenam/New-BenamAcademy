# قرارداد API — راهنمای تیم بک‌اند

این سند قرارداد درخواست‌ها و پاسخ‌های موردانتظار فرانت‌اند است. بک‌اند در ریپوی جداگانه/پوشه‌ای دیگر پیاده می‌شود؛ این پروژه خودش سرور یا mock server ندارد.

---

## خلاصهٔ یک‌دقیقه‌ای

درخواست‌های HTTP برنامه از `appApi` در `scripts/api.js` عبور می‌کنند. هر متد این شیء در حال حاضر مستقیماً با `fetch` درخواست می‌فرستد؛ فایل‌های `api-mock-*.js` در ریپوی فعلی وجود ندارند و `apiMode` سوییچ mock/real نیست.

پیش از بارگذاری `scripts/api.js` می‌توان آدرس پایه را این‌طور تنظیم کرد:

```html
<script>
  window.APP_CONFIG = { apiBaseUrl: "https://api.example.com" };
</script>
<script src="../scripts/api.js"></script>
```

اگر `apiBaseUrl` خالی باشد، مسیرها به همان origin ارسال می‌شوند. برای تست محلی می‌توان از `benamacademyApiBaseUrl` در `localStorage` استفاده کرد؛ مقدار `apiMode` در رفتار درخواست اثری ندارد.

`appApi` مرز اصلی **درخواست‌های HTTP** است، اما تمام وضعیت فرانت را پوشش نمی‌دهد. نشست نمایشی، سبد خرید، برخی تنظیمات/محتوا و چند state پنل هنوز مستقیم در `localStorage` یا `sessionStorage` هستند. این موارد هنگام اتصال بک‌اند خودکار منتقل نمی‌شوند؛ فهرست دقیق‌تر در `docs/تحویل-به-بک‌اند.md` آمده است.

فهرست متدها و payload-ها را در `scripts/api.js` ببینید؛ این سند مشخص می‌کند سرور چه قرارداد و چه کنترل‌های دسترسی‌ای باید داشته باشد.

## قواعد عمومی

| مورد         | قرارداد                                                                 |
| ------------ | ----------------------------------------------------------------------- |
| Base URL     | از `APP_CONFIG.apiBaseUrl` خوانده می‌شود                                |
| Content-Type | `application/json`                                                      |
| احراز هویت   | هدر `Authorization: Bearer <token>` — توکن از پاسخ `/auth/login` می‌آید |
| Timeout      | ۱۰ ثانیه (سمت کلاینت)                                                   |
| موفقیت       | کد ۲xx به‌همراه بدنه JSON                                               |
| خطا          | کد غیر ۲xx به‌همراه `{ "message": "متن فارسی خطا" }`                    |

### قالب خطا

فرانت‌اند فیلد `message` را مستقیماً به کاربر نشان می‌دهد، پس متن آن باید فارسی و قابل‌فهم باشد:

```json
{ "message": "ایمیل یا رمز عبور صحیح نیست." }
```

کدهای وضعیتی که فرانت‌اند به‌طور خاص مدیریت می‌کند:

| کد    | معنا در این پروژه          |
| ----- | -------------------------- |
| `401` | نیاز به ورود مجدد          |
| `409` | تعارض — مثلاً شناسه تکراری |
| `422` | خطای اعتبارسنجی ورودی      |
| `404` | منبع پیدا نشد              |

## اندپوینت‌های عمومی (سایت)

### احراز هویت

| متد    | مسیر                    | بدنه درخواست                       | پاسخ                   |
| ------ | ----------------------- | ---------------------------------- | ---------------------- |
| `POST` | `/auth/register`        | `{ name, email, phone, password }` | `{ token, user }`      |
| `POST` | `/auth/login`           | `{ email, password }`              | `{ token, user }`      |
| `POST` | `/auth/logout`          | —                                  | `{ success: true }`    |
| `GET`  | `/auth/me`              | —                                  | `{ token, user }`      |
| `POST` | `/auth/forgot-password` | `{ email }`                        | `{ success, message }` |

شکل `user`:

```json
{ "id": "user-...", "name": "...", "email": "...", "phone": "..." }
```

**اعتبارسنجی موردانتظار در `/auth/register`:** نام، ایمیل و رمز الزامی — رمز حداقل ۶ کاراکتر — ایمیل تکراری باید `409` برگرداند.

| متد     | مسیر                | بدنه                                     | پاسخ                    |
| ------- | ------------------- | ---------------------------------------- | ----------------------- |
| `PATCH` | `/profile/update`   | `{ name, email, phone, birth, address }` | آبجکت پروفایل به‌روزشده |
| `POST`  | `/profile/password` | `{ currentPassword, newPassword }`       | `{ success: true }`     |

### پشتیبانی و خبرنامه

| متد    | مسیر                    | بدنه                                | پاسخ                   |
| ------ | ----------------------- | ----------------------------------- | ---------------------- |
| `POST` | `/assistant/chat`       | `{ message, conversationId? }`       | `{ answer, conversationId, needsHuman? }` |
| `POST` | `/support/messages`     | `{ name, email, subject, message }` | `{ success, message }` |
| `POST` | `/newsletter/subscribe` | `{ email }`                         | `{ success, message }` |

> **مهم:** پیامی که از مسیر پشتیبانی ثبت می‌شود باید در `GET /admin/messages` قابل مشاهده باشد. این اتصال قبلاً وجود نداشت و اصلاح شد.
>
> `/assistant/chat` باید از توکن احراز هویت‌شده هویت کاربر را سمت سرور استخراج کند؛ `userId`، ایمیل یا کلید سرویس هوش مصنوعی را از کلاینت نپذیرد. بک‌اند باید گفتگو را ذخیره کند، پاسخ agent را همراه `conversationId` برگرداند و در حالت `needsHuman: true` ارجاع پشتیبانی را ثبت کند. کلید ارائه‌دهندهٔ مدل فقط در بک‌اند نگه‌داری شود. فرانت‌اند در نبود صریح endpoint دستیار (`404`، `501` یا `503`) از مسیر `/support/messages` برای ارجاع انسانی استفاده می‌کند.

## اندپوینت‌های پنل مدیریت

همه این مسیرها نیازمند نشست ادمین هستند. سرور باید بدون توکن معتبر، `401` برگرداند.

### محصولات

| متد      | مسیر                  | بدنه               | پاسخ                |
| -------- | --------------------- | ------------------ | ------------------- |
| `GET`    | `/admin/products`     | —                  | آرایه محصولات       |
| `POST`   | `/admin/products`     | آبجکت محصول        | محصول ساخته‌شده     |
| `PATCH`  | `/admin/products/:id` | فیلدهای تغییریافته | محصول به‌روزشده     |
| `DELETE` | `/admin/products/:id` | —                  | `{ success: true }` |

شکل محصول:

```json
{
  "id": "course-1",
  "name": "دوره حسابداری مقدماتی",
  "price": 49000,
  "category": "file",
  "fileUrl": "https://...",
  "img": "https://..."
}
```

**قواعد:** `id` و `name` الزامی‌اند. `id` تکراری باید `409` بدهد.

> نکته درباره `id`: صفحه تک‌مطلب با قرارداد نام‌گذاری محصول را به مطلب وصل می‌کند — `<postId>` برای فایل‌ها و `<postId>-video` برای ویدیو. این قرارداد را حفظ کنید.

### سفارشات

| متد     | مسیر                       | بدنه         | پاسخ            |
| ------- | -------------------------- | ------------ | --------------- |
| `GET`   | `/admin/orders`            | —            | آرایه سفارشات   |
| `POST`  | `/admin/orders`            | آبجکت سفارش  | سفارش ساخته‌شده |
| `PATCH` | `/admin/orders/:id/status` | `{ status }` | سفارش به‌روزشده |

مقادیر مجاز `status`: `success` · `pending` · `cancelled`

### کاربران

| متد      | مسیر                      | بدنه         | پاسخ                |
| -------- | ------------------------- | ------------ | ------------------- |
| `GET`    | `/admin/users`            | —            | آرایه کاربران       |
| `PATCH`  | `/admin/users/:id/status` | `{ status }` | کاربر به‌روزشده     |
| `DELETE` | `/admin/users/:id`        | —            | `{ success: true }` |

شکل کاربر:

```json
{
  "id": 12,
  "name": "مریم حسینی",
  "email": "maryam@example.com",
  "phone": "09121234567",
  "role": "کاربر عادی",
  "status": "فعال",
  "source": "site"
}
```

مقادیر `role`: `کاربر عادی` · `ادمین` · `مدیر سایت` · `مدیر سیستم`
مقادیر `status`: `فعال` · `غیرفعال`

> **مهم:** پاسخ این مسیر باید شامل کاربرانی باشد که از طریق `/auth/register` در سایت ثبت‌نام کرده‌اند. فیلد `source` مشخص می‌کند کاربر از سایت آمده (`site`) یا در پنل ساخته شده.

### پیام‌ها

| متد     | مسیر                        | بدنه                  | پاسخ                  |
| ------- | --------------------------- | --------------------- | --------------------- |
| `GET`   | `/admin/messages`           | —                     | آرایه پیام‌ها         |
| `POST`  | `/admin/messages/:id/reply` | `{ text, adminName }` | پیام با ترد به‌روزشده |
| `PATCH` | `/admin/messages/:id/read`  | —                     | پیام به‌روزشده        |

شکل پیام:

```json
{
  "id": "message-...",
  "sender": "سام به‌نام",
  "email": "sam@example.com",
  "subject": "سوال درباره دوره",
  "text": "متن پیام کاربر",
  "time": "۱۴۰۵/۰۵/۰۵",
  "read": false,
  "source": "site",
  "history": [
    { "sender": "user", "name": "سام به‌نام", "text": "...", "time": "..." },
    { "sender": "admin", "name": "مدیر سایت", "text": "...", "time": "..." }
  ]
}
```

`history` ترد گفتگو است و به‌ترتیب زمانی مرتب می‌شود. مقدار `sender` فقط `user` یا `admin`.

### تنظیمات

| متد   | مسیر              | بدنه               | پاسخ              |
| ----- | ----------------- | ------------------ | ----------------- |
| `GET` | `/admin/settings` | —                  | آبجکت تنظیمات     |
| `PUT` | `/admin/settings` | فیلدهای تغییریافته | تنظیمات ادغام‌شده |

شکل تنظیمات:

```json
{
  "supportEmail": "support@example.ir",
  "supportPhone": "۰۲۱-۱۲۳۴۵۶۷۸",
  "maintenanceMode": false,
  "merchantId": "...",
  "currencyUnit": "toman",
  "adminName": "مدیر کل سایت",
  "adminAvatar": "https://..."
}
```

`PUT` باید **ادغام** کند نه جایگزینی کامل — ارسال `{ maintenanceMode: true }` نباید بقیه فیلدها را پاک کند.

`supportEmail` و `supportPhone` در فوتر تمام صفحات سایت نمایش داده می‌شوند.
`maintenanceMode: true` کل سایت عمومی را قفل می‌کند (پنل ادمین مستثنی است).

#### مدیریت منوی هدر (افزوده‌شده در فاز فرانت‌اند)

بخش «منوی هدر» برای هر دو نقش مدیر و ادمین قابل‌دسترسی است. فعلاً نام‌ها، آیتم‌های افزوده‌شده، حذف‌های ساختاری و دسته‌های ایجادشده از منوی هدر فقط در مرورگر جاری ذخیره می‌شوند: `benamacademyHeaderLabels`، `benamacademyHeaderCustomItems`، `benamacademyHeaderHiddenItems` و `benamacademyHeaderContentCategories`. محتوای محلی در صفحات سایت همان مرورگر دیده می‌شود، اما هنوز به سرور یا مرورگرهای دیگر همگام نمی‌شود.

فرم از نام‌گذاری منوهای فعلی، افزودن منوی اصلی، افزودن عنوان گروهی زیر هر منو، و افزودن زیرگروه زیر هر عنوان/زیرگروه پشتیبانی می‌کند (حداکثر سه سطح). هر منوی اصلی سفارشی در پنل بخش مستقل دارد؛ عنوان گروهی تازه هم‌سطح عنوان‌های موجود همان منو نمایش داده می‌شود و شمارهٔ «عنوان زیرگروه» خودکار از آخرین گروه موجود به‌روز می‌شود. منوی اصلی تازه پس از «قوانین و مقررات» و پیش از آیتم‌های پایانی قرار می‌گیرد. هر منو/زیرگروه پیونددار با مقصد دستهٔ خودکار، هنگام بارگذاری در `siteData` نیز یک دستهٔ قابل‌مدیریت می‌سازد؛ همان دسته در فهرست محتوای سایت و انتخابگر افزودن محتوا می‌آید. محتوای ذخیره‌شدهٔ آن با `categoryKey` و سازوکار فعلی `localStorage` نگه‌داری می‌شود. مدیر فقط عنوان و محل قرارگیری را انتخاب می‌کند: انتخاب ریشه، منوی اصلی می‌سازد؛ انتخاب منوی اصلی، عنوان گروهی؛ و انتخاب عنوان/زیرگروه، پیوند فرزند می‌سازد. برای منوی اصلی و آیتم‌های پیونددار، مقصد دسته خودکار از عنوان ساخته می‌شود؛ عنوان‌های گروهی مقصد ندارند. کلید دسته پس از تغییر عنوان ثابت می‌ماند. اگر مقصدی به دسته‌ای اشاره کند که در `siteData` موجود نیست و از پیوند منوی هدر هم به‌صورت خودکار ساخته نشده، مقصد پیام «دسته پیدا نشد» نشان می‌دهد.

دکمه‌های حذف کنار منوی اصلی، عنوان گروهی و زیرگروه قرار دارند. حذف منو یا عنوان، همهٔ فرزندان وابسته را نیز حذف/پنهان می‌کند؛ حذف یک پیوند فقط همان زیرگروه را حذف می‌کند. بازگردانی ساختار پیش‌فرض، آیتم‌های سفارشی و حذف‌های پنهان را پاک می‌کند.

برای اتصال سراسری در تحویل بک‌اند:

- تنظیمات را با سه فیلد `headerLabels` و `headerCustomItems` و `headerHiddenItems` در `GET/PUT /admin/settings` نگه دارید و `PUT` را به‌شکل ادغام‌شونده پیاده کنید. فقط مدیر و ادمین مجاز به نوشتن باشند.
- یک مسیر عمومیِ فقط‌خواندنی، پیشنهاد‌شده `GET /site/header-menu`، اضافه کنید تا صفحات عمومی هر سه فیلد را دریافت کنند. پاسخ نمونه:

```json
{
  "headerLabels": { "forStudents": "برای دانشجویان", "diploma": "دروس تخصصی دیپلم" },
  "headerCustomItems": [
    { "id": "item-1", "parentKey": "forStudents", "kind": "group", "label": "عنوان تازه", "href": "" },
    { "id": "item-2", "parentKey": "item-1", "kind": "link", "label": "نمونه", "href": "list-page.html?cat=custom-example" }
  ],
  "headerHiddenItems": ["studentsBooks"]
}
```

- کلیدهای نام‌های فعلی و متن‌های پیش‌فرض در `scripts/header-labels.js`، و کلیدهای منوی اصلی/ساختار در `scripts/header-custom-menu.js` فهرست شده‌اند. `parentKey` می‌تواند `root`، کلید هر منو/زیرمنوی فعلی یا شناسهٔ آیتم افزوده‌شده باشد. شناسه‌ها پایدار بمانند و عمق ساختار حداکثر سه سطح باشد.
- عنوان را به‌صورت متن ساده اعتبارسنجی کنید (غیرخالی، حداکثر ۸۰ نویسه) و مقصد پیوند خودکار را از پروتکل‌های اجرایی مانند `javascript:` و `data:` رد کنید. از پذیرش HTML اجرایی جلوگیری و خروجی عمومی را با سیاست کش مناسب ارائه کنید.
- پس از افزودن API، خواندن و ذخیرهٔ محلی در `scripts/header-labels.js` و `scripts/header-custom-menu.js` با لایهٔ `appApi` جایگزین و اطلاعِ «فقط همین مرورگر» از فرم پنل حذف شود.

## نکات امنیتی که سمت سرور باید رعایت شود

فرانت‌اند نمی‌تواند این‌ها را تضمین کند:

1. **احراز هویت پنل ادمین.** در حال حاضر یک گیت سمت کلاینت در `scripts/admin/auth.js` (تابع `requireAdminSession`) وجود دارد که فقط جلوی دسترسی تصادفی را می‌گیرد. سرور باید بدون نشست معتبر، هم فایل `admin.html` و هم تمام مسیرهای `/admin/*` را رد کند.

2. **رمز عبور.** رمز ادمین در حال حاضر در `localStorage` است چون بک‌اندی وجود ندارد. با آمدن سرور، بدنه تابع `verifyAdminPassword` را با یک درخواست به سرور جایگزین کنید. رمزها باید هش شوند (bcrypt یا argon2).

3. **اعتبارسنجی ورودی.** تمام اعتبارسنجی‌های سمت کلاینت صرفاً برای تجربه کاربری‌اند و باید سمت سرور تکرار شوند.

4. **پاک‌سازی خروجی.** پنل در جاهایی از `innerHTML` استفاده می‌کند. داده‌ای که از سرور می‌آید باید پاک‌سازی‌شده باشد، یا حداقل مطمئن شوید محتوای کاربری هرگز شامل HTML اجرایی نیست.

## تبلیغات (Ads)

نوار تبلیغاتیِ پایینِ صفحات اصلی، دسته‌بندی و مطلب که از زیر بالا می‌آید،
حین اسکرول ثابت می‌ماند و با دکمه‌ی × برای آن نشست بسته می‌شود (عکس + متن

- لینک). مدیریت کامل (افزودن/ویرایش/حذف/فعال‌سازی) از تب «تبلیغات» پنل.

### عمومی

| متد   | مسیر   | پاسخ                           |
| ----- | ------ | ------------------------------ |
| `GET` | `/ads` | آرایه‌ای از تبلیغ‌های **فعال** |

فقط تبلیغ‌های `active: true` برمی‌گردند. فیلتر بر اساس صفحه (`home`/`list`/`single`) سمت کلاینت است.

### پنل

نیازمند نشست ادمین/مدیر.

| متد      | مسیر             | بدنه               | پاسخ                   |
| -------- | ---------------- | ------------------ | ---------------------- |
| `GET`    | `/admin/ads`     | —                  | آرایه‌ی همه‌ی تبلیغ‌ها |
| `POST`   | `/admin/ads`     | آبجکت تبلیغ        | تبلیغ ساخته‌شده        |
| `PATCH`  | `/admin/ads/:id` | فیلدهای تغییریافته | تبلیغ به‌روزشده        |
| `DELETE` | `/admin/ads/:id` | —                  | `{ success: true }`    |

شکل تبلیغ:

```json
{
  "id": "ad-...",
  "title": "عنوان",
  "text": "متن کوتاه",
  "image": "https://...",
  "link": "https://...",
  "linkText": "مشاهده",
  "pages": ["home", "list", "single"],
  "delay": 0,
  "active": true
}
```

قواعد: `title` الزامی (`422`). `id` تکراری `409`. `pages` خالی یعنی هر سه صفحه. `delay` بر حسب ثانیه؛ `0` یعنی بلافاصله.

### fallback موقت برای تست فرانت‌اند

تا زمان آماده‌شدن مسیرهای تبلیغات، اگر درخواست با statusهای `0`, `404`, `405`, `501`, `502`, `503` یا `504` شکست بخورد، adapter تبلیغ‌ها از کلید `benamacademyAds` در `localStorage` استفاده می‌کند. پنل پیام می‌دهد که تغییر فقط در همین مرورگر ذخیره شده؛ این داده با دستگاه‌های دیگر همگام نمی‌شود و جای بک‌اند/مجوز سمت سرور را نمی‌گیرد. پاسخ‌های احراز هویت و اعتبارسنجی مثل `401`, `403` و `422` هرگز به ذخیرهٔ محلی تبدیل نمی‌شوند.

برای خاموش‌کردن fallback موقت، پیش از بارگذاری `scripts/api.js` مقدار زیر را تنظیم کنید:

```js
window.APP_CONFIG = { ...window.APP_CONFIG, adsLocalFallback: false };
```

## اندپوینت‌های افزوده‌شده در بازبینی نهایی

پنج قابلیت فقط در `localStorage` زندگی می‌کردند و هیچ مسیری نداشتند. یعنی بعد از اتصال سرور، همچنان در مرورگر می‌ماندند و هر اپراتور داده متفاوتی می‌دید.

### مجوز دانلود

```
POST /commerce/entitlements   →  ["acc-101", "acc-102"]
```

فهرست محصولاتی که این کاربر حق دانلودشان را دارد.

**مهم:** قبلاً از کلید `benamacademyPurchasedProducts` در مرورگر خوانده می‌شد. یعنی:

- کاربری که پول داده بود، در مرورگر دیگر دسترسی نداشت
- هر کسی با یک خط در کنسول، قفل همه فایل‌ها را باز می‌کرد

**سرور باید این را از جدول سفارش‌ها بسازد** و هرگز به فهرستی که کلاینت می‌فرستد اعتماد نکند.

### اعلان‌ها

```
GET    /admin/notifications
POST   /admin/notifications              // idempotent روی id
PATCH  /admin/notifications/:id/read
DELETE /admin/notifications/:id
DELETE /admin/notifications              // حذف همه
```

**نکته امنیتی:** قانون دسترسی باید سمت سرور اعمال شود. ردیف‌های `staff` و `report` **نباید اصلاً** برای نقش «ادمین» ارسال شوند. فیلتر سمت کلاینت فقط برای نمایش است.

### سابقه تغییرات کارکنان

```
GET  /admin/audit/:staffId
POST /admin/audit/:staffId
```

سند تغییرات پروفایل مدیران و ادمین‌هاست. باید فقط-افزودنی باشد و از مرورگری که در آن ساخته شده جان سالم به در ببرد.

### آیتم‌های محتوای سایت

```
GET    /admin/content-items
POST   /admin/content-items       // ۴۰۹ برای شناسه تکراری
DELETE /admin/content-items/:id
```

در فرم افزودن محتوای فرانت‌اند، شناسه به‌صورت خودکار و یکتا ساخته می‌شود و ادمین نیازی به واردکردن آن ندارد. شناسه‌های آیتم‌های قبلی ثابت می‌مانند؛ ترتیب نمایش هر دسته جداگانه در `benamacademyContentItemOrder` ذخیره می‌شود تا آیتم تازه اول بیاید و ترتیب قبلی‌ها حفظ شود. در پیاده‌سازی بک‌اند نیز ترتیب باید فیلدی مستقل از `id` باشد تا جابه‌جایی ترتیب لینک‌ها و ارجاعات محتوا را نشکند.

## نکته درباره نوشتن دوتایی

پنل برای سرعت نمایش، اعلان و سابقه را همزمان در حافظه محلی و روی سرور می‌نویسد. برای همین **مسیرهای POST باید idempotent باشند**:

- اعلان: بر اساس `id`
- سابقه: بر اساس `date` + `text`

اگر سرور این را رعایت نکند، هر رویداد دوبار ثبت و دوبار شمرده می‌شود.
